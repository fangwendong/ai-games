# OPC 探索

> 一个人 + AI + 一台海外服务器，如何搭建游戏工作室与量化交易系统

## 先说结论

过去，一个人想同时做游戏和量化交易，最难的不是写出某段代码，而是承担一整套团队职能：产品设计、开发、测试、部署、数据维护、监控和复盘。

大模型并没有消灭这些工作，但它把很多工作的启动成本降了下来。一个可行的 OPC（One Person Company，一人公司）形态是：

- 人负责目标、取舍、验收和风险；
- ChatGPT/Codex 负责研究、编码、测试、文档和重复操作；
- Git 仓库负责保存事实和变更历史；
- 一台长期在线的服务器负责运行服务、任务和监控；
- 游戏与量化共用工程基础设施，但隔离运行权限和风险边界。

这套组合的价值，不是“让 AI 自动赚钱”，而是让一个人有能力维护过去需要数个角色才能维护的工程系统。

## 第一笔投入：买的不是一个答案，而是一套工作流

这里说的“购买 GPT 账号”，准确做法是注册自己的 OpenAI 账号，并从官方渠道订阅适合自己的 ChatGPT 套餐。不要购买来路不明的成品账号，也不要多人共享登录凭据。OpenAI 的[账号共享政策](https://help.openai.com/en/articles/10471989)明确说明账号应由创建者本人使用；第三方账号还会带来封号、支付信息和工作数据泄露风险。

对个人探索者，ChatGPT 订阅可以覆盖对话、研究和 Codex 交互式开发。需要让自己的程序直接调用模型时，还要单独开通 OpenAI API。ChatGPT 与 API 是两套独立的计费系统，订阅费用不会自动变成 API 额度，详见 OpenAI 的[计费说明](https://help.openai.com/en/articles/9039756-billing-settings-in-chatgpt-vs-platform)。

一个稳妥的起步清单是：

1. 从 OpenAI 官方入口注册个人账号并开启双因素认证。
2. 根据使用频率选择 ChatGPT 套餐，不在文章或脚本中写死套餐价格。
3. 在服务器上安装 Codex CLI，通过自己的 ChatGPT 账号登录；只有程序化 API 调用才单独配置 API key。
4. 给 API 设置充值或预算上限，避免自动化任务失控产生意外费用。
5. 账号、API key、服务器 SSH key 和券商凭据全部分开管理。

## 为什么选择东南亚服务器

东南亚节点（例如新加坡）通常适合作为中文开发者的海外工程中枢：它可以长期在线运行 Git、CI、Web 服务、定时任务和券商客户端，同时让开发终端、游戏预览与交易基础设施集中在一台可控机器上。

选择服务器时，比“最低价格”更重要的是：

- 机房和云厂商稳定，支持快照和重装；
- 到自己所在地、代码托管平台和目标服务的网络质量可接受；
- 至少具备 2 核 CPU、4 GiB 内存和独立数据盘；
- 可以限制入站端口并配置 SSH key；
- 所在地区、账号注册和服务使用符合当地法律及各产品条款。

服务器是工程基础设施，不应被用来规避产品的地区限制、身份要求或支付规则。

## 一台机器上的总体架构

```text
个人电脑 / 手机
       |
       | SSH、Git、ChatGPT/Codex
       v
东南亚云服务器
  |-- Git 仓库与多个 worktree
  |-- 游戏工作室
  |     |-- 静态 Web 原型
  |     |-- Godot 项目
  |     `-- Nginx / 试玩环境
  |-- 量化交易系统
  |     |-- 历史行情与回测
  |     |-- IB Gateway / IBC
  |     |-- 实时行情缓存
  |     |-- 策略、风控与订单边界
  |     `-- 心跳、轮询与收盘保护
  `-- 共同基础设施
        |-- botmux 任务编排
        |-- AGENTS.md / docs / skills
        |-- 资源巡检、日志轮转与备份
        `-- Git 提交、测试与回滚
```

游戏和量化可以共用服务器、Git、文档和 AI 协作方式，但不能共用敏感权限。游戏进程不需要读取券商配置，研究代码也不应直接拥有实盘下单权限。

## 把 AI 变成可管理的工作室

### 1. 用仓库保存上下文

聊天记录会散失，仓库不会。项目结构、运行命令、验收方法和风险边界都应该进入版本控制：

- `README.md` 说明项目是什么、如何启动；
- `AGENTS.md` 告诉 AI 在这个仓库中如何工作；
- `docs/` 保存运行手册、研究结论和复盘；
- `skills/` 沉淀可以复用的工作流；
- 测试保存“什么叫正确”，Git 提交保存“为什么改变”。

Codex 官方手册把 `AGENTS.md` 定位为仓库内可自动加载的持久指导文件。实践中，主文件应保持清晰，再路由到各子项目文档，避免每个新会话都重新解释背景。

### 2. 用 worktree 隔离任务

不同任务使用独立 Git worktree：游戏功能、策略研究、实盘修复各自在自己的目录和分支中完成。这样可以同时推进多个方向，又不会让实验参数覆盖实盘配置。

典型流程是：

```bash
git worktree add ../project-wt-feature -b wt/feature
```

每项改动都遵循“检查现状 → 小范围修改 → 自动测试 → 人工验收 → 提交推送 → 明确部署”的链路。开发目录的变更不会自动进入实盘目录，部署必须是显式动作。

### 3. 让文档成为系统的一部分

遇到一次故障，只在聊天里解决，下一次还会重复。真正的 OPC 杠杆来自沉淀：

- 行情缺失，形成下载、完整性校验和补齐手册；
- IB 掉线，形成 Gateway 启动、2FA 和 heartbeat 手册；
- 回测与实盘不一致，形成撮合口径和交易复盘文档；
- 巡检误报，形成阈值、阶段基线和红绿摘要规范。

文档必须能从 `AGENTS.md` 路由到，否则对下一位 agent 来说，它等于不存在。

## 游戏工作室：快速完成可玩的闭环

游戏方向适合先用低成本原型验证乐趣，再决定是否扩大投入。

### Web 原型

HTML、CSS 和 JavaScript 适合在数小时内验证核心玩法。一个合格原型至少要有：

- 明确目标；
- 可理解的操作；
- 挑战和反馈；
- 胜负条件；
- 快速重开；
- 桌面端与移动端基本可用。

原型可由 Nginx 托管在服务器上，通过独立域名或受保护的测试地址分享。AI 可以快速生成素材和代码，但“是否好玩”仍要靠真人试玩。

### Godot 项目

当玩法成立后，再迁移到 Godot 这样的完整引擎。AI 负责场景脚本、状态机、UI 和测试清单，人负责节奏、手感、视觉一致性和范围控制。

每次交付至少同时验证：项目能启动、核心循环可玩、失败后能重开、输入和 UI 没有明显问题。仅仅“编译通过”不等于游戏完成。

### 游戏生产线

```text
想法 -> 一页设计 -> Web/Godot 原型 -> 本地试玩
     -> 修正核心循环 -> 自动化检查 -> 部署试玩版
     -> 收集反馈 -> 复盘并沉淀技能
```

OPC 的优势不是一次做很多游戏，而是让“从想法到可试玩版本”的周期越来越短。

## 量化交易系统：先工程正确，再谈策略收益

量化系统和游戏最大的区别是：游戏 bug 影响体验，交易 bug 可能直接损失资金。因此，AI 可以帮助开发和巡检，但不能替代账户所有者承担交易决策和风险。

### 系统分层

一个可维护的 IBKR 量化系统至少分为：

1. **数据层**：历史行情、实时行情、交易日历和公司行动处理。
2. **研究层**：策略、参数、成本模型和样本外回测。
3. **经纪商边界**：连接 IB Gateway/TWS，读取行情和提交订单。
4. **风控层**：仓位上限、每日开仓次数、止盈止损和收盘清仓。
5. **执行层**：轮询、行情缓存、订单状态和幂等保护。
6. **运维层**：heartbeat、日志轮转、定时启停、资源巡检和告警。
7. **复盘层**：真实成交、佣金、滑点与回测差异记录。

### 从模拟盘开始

先在 paper account 验证连接、行情、订单状态和退出逻辑，再考虑小资金实盘。IBKR 官方说明 TWS API/Web API 可用于模拟账户，但模拟成交与真实市场仍有差异，例如部分订单类型和盘口深度，参见 [IBKR Paper Trading Account](https://ibkrcampus.com/campus/glossary-terms/paper-trading-account/)。

安全默认值应该是：

```text
READONLY=true
DRY_RUN=true
ALLOW_LIVE_TRADING=false
```

进入实盘必须同时满足多个显式开关，而不是修改一个布尔值就能下单。只读检查、回测、策略研究和实盘执行要使用不同命令与配置边界。

### 回测必须接近实盘

回测最危险的不是算错，而是“看起来太好”。至少要处理：

- 佣金和滑点；
- 信号生成时间与下一次可成交时间；
- 1 分钟/5 分钟 bar 的撮合口径；
- 同一根 bar 同时触发止盈止损时的保守顺序；
- 复权、拆股/合股和交易日历；
- 数据缺失以及不同交易所行情混用；
- 每日最新余额复投时的路径依赖；
- 样本外、分段和走步验证，防止过拟合。

实盘与回测必须共享策略决策函数，行情来源和成本口径也要尽量一致。每次真实交易结束后，用当天行情重放并记录差异，系统才能逐步逼近真实成交。

### 实时执行不是一个死循环

稳定的实盘链路通常由多个小进程组成：

- 一个进程持续订阅实时报价，只保留有界缓存并原子写文件；
- 一个进程预先计算交易日历和已完成的 5 分钟 bars；
- 策略轮询读取缓存，缓存过旧时立即回退到经纪商接口；
- 独立 heartbeat 只检查连接，不读账户、不交易；
- 开盘任务启动轮询，收盘任务暂停轮询；
- 无论策略信号如何，收盘前都有强制清仓保护。

这比让策略每分钟临时建立全部上下文更快，也更容易定位行情、策略和订单分别出了什么问题。

## 安全边界：这部分不能交给“感觉”

### 账号与密钥

- OpenAI、云服务器、GitHub 和 IBKR 都开启双因素认证；
- SSH 禁止密码登录，使用独立密钥；
- `.env`、API key、券商配置和运行状态不进入 Git；
- 日志和分享文档不得出现账号、余额、订单 ID、IP 或 token；
- 凭据一旦误提交，先撤销轮换，再处理 Git 历史。

GitHub 的[秘密扫描说明](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)也强调，硬编码凭据会带来未授权访问和费用风险。不能把 secret scanning 当作唯一防线，最好的 secret 是从未进入仓库的 secret。

### 网络与进程

- 防火墙只开放 SSH、HTTP/HTTPS 等必要端口；
- IB API 端口只允许受信网络访问；
- 开发、回测和实盘使用不同 checkout；
- 每个后台服务单实例运行，使用锁防止重复启动；
- 缓存有数量/时间上限，日志有轮转和保留期；
- 服务器资源巡检只观察并报警，不擅自 kill 未知进程。

### AI 权限

给 AI 的权限遵循最小化原则：

- 解释和诊断任务默认只读；
- 修改代码后必须测试和展示 diff；
- 推送、部署和实盘切换是不同动作；
- 实盘验证默认强制只读、dry-run、禁止交易；
- 真实下单、取消订单和改变风险预算必须有明确授权；
- 任何输出都不能暴露账户细节。

## 日常运行节奏

### 每天

- 检查 CPU、内存、磁盘、botmux、Gateway、heartbeat 和缓存进程；
- 交易日前补齐历史行情并验证最近交易日完整性；
- 盘前确认任务、策略版本、数据来源和安全开关；
- 盘中观察决策摘要、行情时间、快慢线、持仓状态和退出距离；
- 收盘后确认清仓、停止轮询，并记录净收益率、佣金和执行差异。

### 每周

- 更新系统和依赖，但不在开盘前临时升级；
- 检查备份、日志大小和数据盘空间；
- 复盘策略与实盘差异，而不是只看盈亏；
- 清理明确不可恢复的会话和过期任务；
- 将重复出现的问题补进 docs、测试或自动化检查。

### 每月

- 汇总游戏交付、用户反馈和下一步优先级；
- 对策略做分段、样本外和成本敏感性验证；
- 盘点 ChatGPT/API、服务器、域名、行情和交易费用；
- 检查自己是否在维护太多项目，主动停止低价值方向。

## 成本应该怎么算

不要只计算“GPT 账号 + 服务器”两个数字。完整成本包括：

| 类别 | 典型内容 | 控制方式 |
|---|---|---|
| AI | ChatGPT 订阅、可选 API 调用 | 选择合适套餐，设置 API 预算 |
| 云资源 | 服务器、快照、数据盘、流量 | 从小规格开始，监控后扩容 |
| 开发发布 | 域名、素材、应用商店费用 | 原型阶段尽量使用开源工具 |
| 交易基础设施 | 券商、行情订阅、佣金 | 按真实账单回填成本模型 |
| 隐性成本 | 维护、故障、研究时间 | 自动化重复任务，停止无效方向 |

真正昂贵的通常不是服务器，而是没有边界地同时做太多事情。OPC 的核心财务纪律，是让每项长期成本都对应一个可验证的产出。

## 一个可复制的 30 天路线

### 第 1 周：基础设施

- 注册个人官方账号并开启 2FA；
- 购买合规的东南亚云服务器；
- 配置 SSH、防火墙、Git、Codex 和备份；
- 建立仓库、`AGENTS.md`、文档索引和 worktree 规范。

### 第 2 周：游戏闭环

- 写一页游戏设计；
- 完成一个 Web 或 Godot 可玩原型；
- 部署试玩地址；
- 找到至少一名真实玩家测试并记录问题。

### 第 3 周：量化闭环

- 只连接模拟账户；
- 下载、校验并统一保存历史行情；
- 完成一个包含交易成本的基线回测；
- 用 dry-run 运行策略，验证信号、风控和收盘退出。

### 第 4 周：运营闭环

- 增加 heartbeat、缓存、日志轮转和资源巡检；
- 模拟网络断开、缓存过期、行情缺失和进程重复启动；
- 建立游戏周报与交易复盘模板；
- 删除不再使用的实验，形成第一版 SOP。

30 天的目标不是靠游戏或交易盈利，而是证明一个人可以稳定地完成“想法 → 实现 → 验证 → 部署 → 监控 → 复盘”的完整循环。

## 我踩过的几个坑

1. **把 ChatGPT 订阅当成 API 套餐。** 两者独立计费，要先决定是交互式开发还是程序调用。
2. **让所有任务共用一个目录。** 实验配置很容易覆盖实盘；worktree 和显式部署能降低风险。
3. **只看短期回测最好参数。** 样本少、重复试参会制造虚假的确定性。
4. **回测撮合过于乐观。** 用 bar 的最高最低价假设必然成交，往往高估收益。
5. **后台进程无限缓存和写日志。** 没有上限与轮转，服务器迟早被内存或磁盘拖垮。
6. **监控只有“正常/异常”。** 好的摘要要把最重要异常放首行，同时保留底层指标便于定位。
7. **问题只留在聊天里。** 没有进入文档和测试的经验，很难在下一次复用。

## 最后的边界

游戏工作室和量化系统可以由同一个人、同一套 AI 工具和同一台服务器起步，但两者的成功标准不同：游戏要证明有人愿意玩，策略要证明经过成本、样本外和真实执行后仍有可接受的风险收益。

AI 擅长加速执行，不擅长替你承担责任。服务器可以 24 小时运行，策略可以自动下单，但是否上线、投入多少资金、何时停止，必须始终由人决定。

这才是 OPC 探索真正值得分享的地方：不是一个人假装成一家公司，而是一个人借助 AI，把公司的流程、纪律和复盘能力真正建立起来。
