# OPC 探索

> 一个人 + AI + 一台海外服务器，如何搭建游戏工作室与量化交易系统

## 先说结论

过去，一个人想同时做游戏和量化交易，最难的不是写出某段代码，而是承担一整套团队职能：产品设计、开发、测试、部署、数据维护、监控和复盘。

大模型并没有消灭这些工作，但它把很多工作的启动成本降了下来。一个可行的 OPC（One Person Company，一人公司）形态是：

- 人负责目标、取舍、验收和风险；
- ChatGPT/Codex 负责研究、编码、测试、文档和重复操作；
- Git 仓库负责保存事实和变更历史；
- 一台长期在线的服务器负责运行服务、任务和监控；
- 游戏与量化共用工程基础设施，但隔离运行权限和风险边界。

这套组合的价值，不是“让 AI 自动赚钱”，而是让一个人有能力维护过去需要数个角色才能维护的工程系统。

## 第一笔投入：买的不是一个答案，而是一套工作流

这里说的“购买 GPT 账号”，准确做法是注册自己的 OpenAI 账号，并从官方渠道订阅适合自己的 ChatGPT 套餐。不要购买来路不明的成品账号，也不要多人共享登录凭据。OpenAI 的[账号共享政策](https://help.openai.com/en/articles/10471989)明确说明账号应由创建者本人使用；第三方账号还会带来封号、支付信息和工作数据泄露风险。

对个人探索者，ChatGPT 订阅可以覆盖对话、研究和 Codex 交互式开发。需要让自己的程序直接调用模型时，还要单独开通 OpenAI API。ChatGPT 与 API 是两套独立的计费系统，订阅费用不会自动变成 API 额度，详见 OpenAI 的[计费说明](https://help.openai.com/en/articles/9039756-billing-settings-in-chatgpt-vs-platform)。

一个稳妥的起步清单是：

1. 从 OpenAI 官方入口注册个人账号并开启双因素认证。
2. 根据使用频率选择 ChatGPT 套餐，不在文章或脚本中写死套餐价格。
3. 在服务器上安装 Codex CLI，通过自己的 ChatGPT 账号登录；只有程序化 API 调用才单独配置 API key。
4. 给 API 设置充值或预算上限，避免自动化任务失控产生意外费用。
5. 账号、API key、服务器 SSH key 和券商凭据全部分开管理。

## 为什么选择东南亚服务器

东南亚节点（例如新加坡）通常适合作为中文开发者的海外工程中枢：它可以长期在线运行 Git、CI、Web 服务、定时任务和券商客户端，同时让开发终端、游戏预览与交易基础设施集中在一台可控机器上。

选择服务器时，比“最低价格”更重要的是：

- 机房和云厂商稳定，支持快照和重装；
- 到自己所在地、代码托管平台和目标服务的网络质量可接受；
- 至少具备 2 核 CPU、4 GiB 内存和独立数据盘；
- 可以限制入站端口并配置 SSH key；
- 所在地区、账号注册和服务使用符合当地法律及各产品条款。

服务器是工程基础设施，不应被用来规避产品的地区限制、身份要求或支付规则。

## 一台机器上的总体架构

```text
手机 / 电脑上的飞书
          |
          | 文字、图片、文件、@机器人、话题上下文
          v
     飞书聊天机器人
          |
          | 接收事件 / 发送回复
          v
        botmux
  |-- 按聊天与话题路由到对应 Codex 会话
  |-- 创建、恢复、清理和隔离会话
  |-- 分发即时任务与定时任务
  `-- 将进度、结果和告警送回原飞书话题
          |
          v
   Codex 执行与编排层
  |-- 读取 AGENTS.md / docs / skills
  |-- 操作 Git 仓库与独立 worktree
  |-- 运行命令、测试、浏览器和 Godot
  |-- 调用被授权的外部接口
  `-- 按权限边界提交、推送或部署
          |
          v
    东南亚服务器上的工作负载
  |-- 游戏：Web 原型、Godot、Nginx 试玩环境
  |-- 量化：历史数据、回测、IB Gateway、缓存、策略与风控
  `-- 运维：tmux、定时任务、心跳、巡检、日志和备份
          |
          | 执行结果 / 状态 / 告警
          v
Codex -> botmux -> 飞书聊天机器人 -> 原飞书话题
```

这套架构的日常入口是飞书，而不是 SSH。用户在手机或电脑的飞书话题里描述任务，机器人把消息交给 botmux；botmux 根据聊天、话题和会话关系把任务路由给 Codex。Codex 在服务器上读取仓库上下文并使用被授权的工具执行，期间的进度、最终结果和定时告警再沿原路径回到同一个飞书话题。

因此，开发游戏、修改代码、运行测试、查询运行状态、生成文档、执行回测和维护服务，都可以从飞书发起。这里的“任何任务”指服务器权限和用户明确授权范围内可执行的任务；真实交易、删除资源、暴露凭据等高风险动作仍然受安全边界约束。

SSH 是机器人或 botmux 故障时的备用运维入口，也用于最初安装和底层恢复，不是日常协作主入口。游戏和量化可以共用服务器、Git、文档和 AI 协作方式，但不能共用敏感权限。游戏进程不需要读取券商配置，研究代码也不应直接拥有实盘下单权限。

### 飞书、botmux 与 Codex 各自负责什么

| 层 | 职责 | 不负责什么 |
|---|---|---|
| 飞书 | 用户入口、话题协作、图片/文件输入、结果展示和人工确认 | 不直接执行服务器命令 |
| 飞书聊天机器人 | 接收飞书事件并代表系统回复消息 | 不理解代码仓库，也不自行决定任务 |
| botmux | 把飞书消息映射到 Codex 会话，维护上下文、并发、定时任务和消息回传 | 不替代 Codex 编码，也不绕过权限边界 |
| Codex | 理解意图、读取仓库规范、调用工具、修改代码、测试、诊断和交付 | 不拥有无限权限，高风险动作仍需明确授权 |
| 服务器与仓库 | 保存代码、数据、文档和运行进程，提供可验证的执行环境 | 不替代人的产品判断和交易责任 |

飞书话题提供业务上下文，botmux 提供可靠路由，Codex 提供执行能力，服务器提供持续在线的环境。这四层组合后，手机上的一句话才会变成一次可追踪、可测试、可回传的真实任务。

## 把 AI 变成可管理的工作室

### 1. 用仓库保存上下文

聊天记录会散失，仓库不会。项目结构、运行命令、验收方法和风险边界都应该进入版本控制：

- `README.md` 说明项目是什么、如何启动；
- `AGENTS.md` 告诉 AI 在这个仓库中如何工作；
- `docs/` 保存运行手册、研究结论和复盘；
- `skills/` 沉淀可以复用的工作流；
- 测试保存“什么叫正确”，Git 提交保存“为什么改变”。

Codex 官方手册把 `AGENTS.md` 定位为仓库内可自动加载的持久指导文件。实践中，主文件应保持清晰，再路由到各子项目文档，避免每个新会话都重新解释背景。

### 2. 用 worktree 隔离任务

不同任务使用独立 Git worktree：游戏功能、策略研究、实盘修复各自在自己的目录和分支中完成。这样可以同时推进多个方向，又不会让实验参数覆盖实盘配置。

典型流程是：

```bash
git worktree add ../project-wt-feature -b wt/feature
```

每项改动都遵循“检查现状 → 小范围修改 → 自动测试 → 人工验收 → 提交推送 → 明确部署”的链路。开发目录的变更不会自动进入实盘目录，部署必须是显式动作。

### 3. 让文档成为系统的一部分

遇到一次故障，只在聊天里解决，下一次还会重复。真正的 OPC 杠杆来自沉淀：

- 行情缺失，形成下载、完整性校验和补齐手册；
- IB 掉线，形成 Gateway 启动、2FA 和 heartbeat 手册；
- 回测与实盘不一致，形成撮合口径和交易复盘文档；
- 巡检误报，形成阈值、阶段基线和红绿摘要规范。

文档必须能从 `AGENTS.md` 路由到，否则对下一位 agent 来说，它等于不存在。

## 游戏工作室：快速完成可玩的闭环

游戏方向适合先用低成本原型验证乐趣，再决定是否扩大投入。

### 游戏开发用到的 Skills

这里的 Skill 不是一个“万能提示词”，而是一份可重复执行的专业工作流。它告诉 Codex 应该先做什么、完成标准是什么、如何验证，以及哪些常见错误不能再犯。

| Skill / 能力 | 在工作室中的作用 | 产出或验收标准 |
|---|---|---|
| `godot-game-prototyper` | 规划和实现 Godot 4 可玩原型，约束场景、GDScript、输入、UI、调参和重开流程 | 必须有目标、操作、挑战、反馈、胜负和快速重开；运行 headless 检查并完成首分钟试玩 |
| 图像生成能力 | 为房间、角色、背景、图标和占位素材生成或修改位图 | 先看现有素材再编辑；生成结果必须放回具体游戏并检查裁切、对比度和可读性 |
| 仓库级 `AGENTS.md` | 给所有 agent 提供目录规范、启动命令、验证方法和质量底线 | 新会话进入仓库后不用重新口述项目规则 |
| 项目 `design.md` | 保存玩法循环、第一局体验、调参常量和试玩结论 | 每次迭代能说明改了哪个体验问题，而不只是罗列代码变更 |
| 可复用 `skills/` | 把多个游戏都会遇到的制作方法从单个项目中抽出来 | 后续游戏可以复用同一套原型、调优和交付标准 |

`godot-game-prototyper` 是当前仓库真正落地的游戏 Skill。它强调“小而完整”：与其生成一个能启动但没有目标的空场景，不如先完成一屏可玩、能失败、能胜利、能立即重开的循环。图像生成则是辅助能力，不能替代玩法验证。

### 游戏开发用到的工具

| 工具 | 具体用途 | 为什么适合 OPC |
|---|---|---|
| ChatGPT / Codex | 需求拆解、写代码、修 bug、检查仓库、补文档和执行验证 | 一个人可以在策划、程序、测试和运维角色间快速切换 |
| HTML / CSS / JavaScript | 制作单文件或纯静态浏览器游戏 | 零构建或低构建成本，几分钟即可启动和分享 |
| Python `http.server` | 本地启动静态游戏预览 | 无需额外框架，适合快速验收 |
| Godot 4 / GDScript | 制作场景化、可扩展的 2D 游戏 | 免费开源，场景和脚本适合小步迭代，也支持桌面/Web 导出 |
| 浏览器与 Playwright | 检查桌面/移动视口、交互、空白画面和文字遮挡 | 把一部分“人工点点看”变成可重复验证 |
| 图像生成工具 | 快速制作方向稿、背景和占位资产 | 原型不再因为缺少美术完全停滞，但最终仍需人工统一风格 |
| Nginx | 托管静态试玩版和配置访问入口 | 资源占用低，一台小服务器能同时托管多个原型 |
| Git / GitHub / worktree | 保存版本、并行开发、评审 diff 和回滚 | 让 AI 的每次修改可追踪，实验不会覆盖稳定版本 |
| 飞书聊天机器人 + botmux | 将飞书话题映射到服务器 Codex 会话，分发即时/定时任务并把进度、结果和告警发回原话题 | 手机也能完成任务发起、确认和跟踪，长任务不依赖本地电脑持续在线 |

工具之间不是平铺关系，而是一条链：用户在飞书提出目标，聊天机器人把消息交给 botmux，botmux 路由给 Codex；Codex 在 worktree 中实现，Skill 约束交付质量，浏览器或 Godot 验证可玩性，Git 保存结果，Nginx 发布试玩版，最终结果再经 botmux 回到原飞书话题。

### Web 原型

HTML、CSS 和 JavaScript 适合在数小时内验证核心玩法。一个合格原型至少要有：

- 明确目标；
- 可理解的操作；
- 挑战和反馈；
- 胜负条件；
- 快速重开；
- 桌面端与移动端基本可用。

原型可由 Nginx 托管在服务器上，通过独立域名或受保护的测试地址分享。AI 可以快速生成素材和代码，但“是否好玩”仍要靠真人试玩。

### Godot 项目

当玩法成立后，再迁移到 Godot 这样的完整引擎。AI 负责场景脚本、状态机、UI 和测试清单，人负责节奏、手感、视觉一致性和范围控制。

每次交付至少同时验证：项目能启动、核心循环可玩、失败后能重开、输入和 UI 没有明显问题。仅仅“编译通过”不等于游戏完成。

### 游戏生产线

```text
想法 -> 一页设计 -> Web/Godot 原型 -> 本地试玩
     -> 修正核心循环 -> 自动化检查 -> 部署试玩版
     -> 收集反馈 -> 复盘并沉淀技能
```

OPC 的优势不是一次做很多游戏，而是让“从想法到可试玩版本”的周期越来越短。

## 量化交易系统：先工程正确，再谈策略收益

量化系统和游戏最大的区别是：游戏 bug 影响体验，交易 bug 可能直接损失资金。因此，AI 可以帮助开发和巡检，但不能替代账户所有者承担交易决策和风险。

### 量化交易用到的 Skills 与运行手册

量化侧目前没有把所有知识塞进一个大型 Skill，而是采用“两层结构”：交易类 Skill 约束外部交易能力和敏感操作，仓库中的专项 runbook 约束本地 IBKR 系统。这样比一个万能 Skill 更容易审查和维护。

| Skill / 手册 | 负责的问题 | 关键边界 |
|---|---|---|
| `ai-trader` Skill | 识别交易信号、跟单、发布和交易平台类请求，提供认证与接口路由规范 | 它不是本地 IBKR 实盘策略的一部分；未明确授权时不连接外部信号平台、不发布信号、不复制交易 |
| 策略基线文档 | 冻结当前策略参数、入场/退出、风险预算和版本契约 | 研究实验不得覆盖实盘参数；变更必须回测、评审并显式部署 |
| 回测调参手册 | 规定佣金、滑点、撮合时序、分段验证和防过拟合方法 | 不用短窗最佳结果证明长期有效，不使用乐观的未来数据 |
| 历史行情手册 | 统一数据目录、下载、完整性检查和增量补齐 | 每次回测前先检查缺失；同一交易日不混用不一致的数据口径 |
| Gateway / heartbeat 手册 | 维护 IB Gateway、IBC、2FA、端口和只读连接检查 | heartbeat 不读账户、不读取交易状态、不下单 |
| 实时报价与上下文缓存手册 | 维护报价订阅、交易日历和已完成 bars 的缓存进程 | 有界缓存、原子写入、单写者锁；过期时立即回退，不无限 sleep |
| 健康巡检手册 | 维护 CPU、内存、磁盘、botmux、IB 和缓存进程检查 | 正常绿标、异常红标；巡检只观察和报警，不擅自重启或 kill 未知进程 |
| 实盘复盘日志 | 汇总每日执行、佣金、退出原因、净收益率和回测差异 | 内容脱敏，不保存账户、订单或执行标识 |

这些运行手册全部从 `AGENTS.md` 路由到文档索引。对 agent 来说，它们就是量化系统的“操作技能”：遇到历史数据问题先读行情手册，遇到 API 连接问题先读 Gateway/heartbeat 手册，而不是临场猜命令。

### 量化交易用到的工具

| 工具 | 具体用途 | 安全或质量控制 |
|---|---|---|
| Python 3.10+ | 策略、回测、CLI、缓存和运维脚本的主要语言 | 模块化分层，避免策略代码直接绕过 broker/risk 边界 |
| `ib-insync` | 封装 IBKR TWS API 的连接、合约、行情和订单调用 | 所有调用集中在 broker 层；明确 client ID、市场数据类型和连接超时 |
| IB Gateway | 连接 IBKR 账户、行情和交易 API | API 端口受限；实盘启用前验证身份、权限和行情订阅 |
| IBC | 自动启动和守护 IB Gateway | 只负责进程生命周期，不能替代 2FA 和交易安全开关 |
| IBKR live 账户与行情权限 | 获取真实的历史/实时行情，并在明确授权后承载实盘订单 | 日常检查强制只读、dry-run、禁止实盘下单；live 连接不等于允许交易 |
| 自研 CLI | 提供 doctor、heartbeat、历史补齐、回测和策略命令 | 只读检查、dry-run 与实盘命令明确分离 |
| 回测引擎 | 重放历史 bars，计算交易成本、盈亏、胜率和回撤 | 信号与成交按时间因果执行，止盈止损口径与实盘对齐 |
| SMART / ARCA 行情 | 提供实时和历史市场数据 | 同一交易日保持统一来源；实盘不静默回退到延迟行情 |
| 共享历史数据盘 | 保存多年 1 分钟/5 分钟 bars | 与系统盘隔离，统一目录复用，回测前审计完整性 |
| 报价缓存进程 | 订阅实时行情并每秒原子刷新有界文件 | 只保留最近时间窗/数量，单实例运行，记录行情年龄 |
| 上下文缓存进程 | 预计算交易日历和已完成的 5 分钟 bars | 每个时间桶刷新，元数据和 OHLCV 严格校验 |
| `pytest` | 覆盖策略、回测、风险、数据守卫、缓存和运行锁 | 改实盘逻辑前跑相关测试，重要变更跑完整测试集 |
| botmux schedule | 安排历史补齐、盘前启动、盘中轮询、收盘停止和健康巡检 | 保护当前交易阶段任务，避免重复任务和过期任务误报 |
| tmux | 承载 Gateway 辅助进程和长期缓存服务 | 服务单实例、可观察、断开 SSH 后继续运行 |
| Linux 资源工具 | 用 `mpstat`、`free`、`df`、`ps` 检查服务器 | 设定 CPU、内存、磁盘阈值，避免回测并发或日志拖垮机器 |
| Git / 独立 checkout | 分离开发回测目录与正在运行的实盘目录 | 提交推送不等于部署；切换实盘必须显式同步并复核 |

量化工具链可以概括成四条路径：

```text
研究：共享历史数据 -> 回测引擎 -> 分段/样本外验证 -> 策略基线
行情：IBKR -> 实时订阅/上下文缓存 -> 新鲜度校验 -> 策略决策
交易：策略决策 -> 风控 -> broker 边界 -> IB Gateway -> 订单状态
运维：botmux/tmux -> heartbeat/巡检 -> 告警 -> 人工处置与复盘
```

这里最重要的不是工具数量，而是职责不混用：`ai-trader` 之类的外部信号能力不能绕过本地风控，回测工具不能写实盘状态，健康巡检不能读取账户或发订单，研究 agent 也不能自动把“表现最好”的参数切到真钱环境。

### 系统分层

一个可维护的 IBKR 量化系统至少分为：

1. **数据层**：历史行情、实时行情、交易日历和公司行动处理。
2. **研究层**：策略、参数、成本模型和样本外回测。
3. **经纪商边界**：连接 IB Gateway/TWS，读取行情和提交订单。
4. **风控层**：仓位上限、每日开仓次数、止盈止损和收盘清仓。
5. **执行层**：轮询、行情缓存、订单状态和幂等保护。
6. **运维层**：heartbeat、日志轮转、定时启停、资源巡检和告警。
7. **复盘层**：真实成交、佣金、滑点与回测差异记录。

### 从 live 账户的只读验证开始

这套系统从一开始就通过 IBKR live 账户权限获取历史行情、回测数据和实盘行情；回测在本地重放这些历史 bars，并不会把回测订单发送给 IBKR。

live 账户连接与真实下单是两件事。连接、heartbeat、行情检查和策略验证默认强制只读、dry-run、禁止实盘交易。只有在策略、风控、任务状态和人工授权全部确认后，才显式开启真实订单通道。

安全默认值应该是：

```text
READONLY=true
DRY_RUN=true
ALLOW_LIVE_TRADING=false
```

允许真实下单必须同时满足多个显式开关，而不是修改一个布尔值就能下单。只读检查、回测、策略研究和实盘执行要使用不同命令与配置边界。

### 回测必须接近实盘

回测最危险的不是算错，而是“看起来太好”。至少要处理：

- 佣金和滑点；
- 信号生成时间与下一次可成交时间；
- 1 分钟/5 分钟 bar 的撮合口径；
- 同一根 bar 同时触发止盈止损时的保守顺序；
- 复权、拆股/合股和交易日历；
- 数据缺失以及不同交易所行情混用；
- 每日最新余额复投时的路径依赖；
- 样本外、分段和走步验证，防止过拟合。

实盘与回测必须共享策略决策函数，行情来源和成本口径也要尽量一致。每次真实交易结束后，用当天行情重放并记录差异，系统才能逐步逼近真实成交。

### 实时执行不是一个死循环

稳定的实盘链路通常由多个小进程组成：

- 一个进程持续订阅实时报价，只保留有界缓存并原子写文件；
- 一个进程预先计算交易日历和已完成的 5 分钟 bars；
- 策略轮询读取缓存，缓存过旧时立即回退到经纪商接口；
- 独立 heartbeat 只检查连接，不读账户、不交易；
- 开盘任务启动轮询，收盘任务暂停轮询；
- 无论策略信号如何，收盘前都有强制清仓保护。

这比让策略每分钟临时建立全部上下文更快，也更容易定位行情、策略和订单分别出了什么问题。

## 安全边界：这部分不能交给“感觉”

### 账号与密钥

- OpenAI、云服务器、GitHub 和 IBKR 都开启双因素认证；
- SSH 禁止密码登录，使用独立密钥；
- `.env`、API key、券商配置和运行状态不进入 Git；
- 日志和分享文档不得出现账号、余额、订单 ID、IP 或 token；
- 凭据一旦误提交，先撤销轮换，再处理 Git 历史。

GitHub 的[秘密扫描说明](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)也强调，硬编码凭据会带来未授权访问和费用风险。不能把 secret scanning 当作唯一防线，最好的 secret 是从未进入仓库的 secret。

### 网络与进程

- 防火墙只开放 SSH、HTTP/HTTPS 等必要端口；
- IB API 端口只允许受信网络访问；
- 开发、回测和实盘使用不同 checkout；
- 每个后台服务单实例运行，使用锁防止重复启动；
- 缓存有数量/时间上限，日志有轮转和保留期；
- 服务器资源巡检只观察并报警，不擅自 kill 未知进程。

### AI 权限

给 AI 的权限遵循最小化原则：

- 解释和诊断任务默认只读；
- 修改代码后必须测试和展示 diff；
- 推送、部署和实盘切换是不同动作；
- 实盘验证默认强制只读、dry-run、禁止交易；
- 真实下单、取消订单和改变风险预算必须有明确授权；
- 任何输出都不能暴露账户细节。

## 日常运行节奏

### 每天

- 检查 CPU、内存、磁盘、botmux、Gateway、heartbeat 和缓存进程；
- 交易日前补齐历史行情并验证最近交易日完整性；
- 盘前确认任务、策略版本、数据来源和安全开关；
- 盘中观察决策摘要、行情时间、快慢线、持仓状态和退出距离；
- 收盘后确认清仓、停止轮询，并记录净收益率、佣金和执行差异。

### 每周

- 更新系统和依赖，但不在开盘前临时升级；
- 检查备份、日志大小和数据盘空间；
- 复盘策略与实盘差异，而不是只看盈亏；
- 清理明确不可恢复的会话和过期任务；
- 将重复出现的问题补进 docs、测试或自动化检查。

### 每月

- 汇总游戏交付、用户反馈和下一步优先级；
- 对策略做分段、样本外和成本敏感性验证；
- 盘点 ChatGPT/API、服务器、域名、行情和交易费用；
- 检查自己是否在维护太多项目，主动停止低价值方向。

## 成本应该怎么算

不要只计算“GPT 账号 + 服务器”两个数字。完整成本包括：

| 类别 | 典型内容 | 控制方式 |
|---|---|---|
| AI | ChatGPT 订阅、可选 API 调用 | 选择合适套餐，设置 API 预算 |
| 云资源 | 服务器、快照、数据盘、流量 | 从小规格开始，监控后扩容 |
| 开发发布 | 域名、素材、应用商店费用 | 原型阶段尽量使用开源工具 |
| 交易基础设施 | 券商、行情订阅、佣金 | 按真实账单回填成本模型 |
| 隐性成本 | 维护、故障、研究时间 | 自动化重复任务，停止无效方向 |

真正昂贵的通常不是服务器，而是没有边界地同时做太多事情。OPC 的核心财务纪律，是让每项长期成本都对应一个可验证的产出。

## 一个可复制的 30 天路线

### 第 1 周：基础设施

- 注册个人官方账号并开启 2FA；
- 购买合规的东南亚云服务器；
- 配置 SSH、防火墙、Git、Codex 和备份；
- 建立仓库、`AGENTS.md`、文档索引和 worktree 规范。

### 第 2 周：游戏闭环

- 写一页游戏设计；
- 完成一个 Web 或 Godot 可玩原型；
- 部署试玩地址；
- 找到至少一名真实玩家测试并记录问题。

### 第 3 周：量化闭环

- 连接 IBKR live 账户，但强制只读、dry-run、禁止实盘下单；
- 下载、校验并统一保存历史行情；
- 完成一个包含交易成本的基线回测；
- 用 dry-run 运行策略，验证信号、风控和收盘退出。

### 第 4 周：运营闭环

- 增加 heartbeat、缓存、日志轮转和资源巡检；
- 模拟网络断开、缓存过期、行情缺失和进程重复启动；
- 建立游戏周报与交易复盘模板；
- 删除不再使用的实验，形成第一版 SOP。

30 天的目标不是靠游戏或交易盈利，而是证明一个人可以稳定地完成“想法 → 实现 → 验证 → 部署 → 监控 → 复盘”的完整循环。

## 我踩过的几个坑

1. **把 ChatGPT 订阅当成 API 套餐。** 两者独立计费，要先决定是交互式开发还是程序调用。
2. **让所有任务共用一个目录。** 实验配置很容易覆盖实盘；worktree 和显式部署能降低风险。
3. **只看短期回测最好参数。** 样本少、重复试参会制造虚假的确定性。
4. **回测撮合过于乐观。** 用 bar 的最高最低价假设必然成交，往往高估收益。
5. **后台进程无限缓存和写日志。** 没有上限与轮转，服务器迟早被内存或磁盘拖垮。
6. **监控只有“正常/异常”。** 好的摘要要把最重要异常放首行，同时保留底层指标便于定位。
7. **问题只留在聊天里。** 没有进入文档和测试的经验，很难在下一次复用。

## 最后的边界

游戏工作室和量化系统可以由同一个人、同一套 AI 工具和同一台服务器起步，但两者的成功标准不同：游戏要证明有人愿意玩，策略要证明经过成本、样本外和真实执行后仍有可接受的风险收益。

AI 擅长加速执行，不擅长替你承担责任。服务器可以 24 小时运行，策略可以自动下单，但是否上线、投入多少资金、何时停止，必须始终由人决定。

这才是 OPC 探索真正值得分享的地方：不是一个人假装成一家公司，而是一个人借助 AI，把公司的流程、纪律和复盘能力真正建立起来。
